# 验证内容真实性

对文章内容进行严格的真实性验证，确保所有信息都有可追溯来源，经过交叉验证，符合事实。

## 核心原则

- **零容忍编造**：任何编造的信息都必须移除
- **可追溯性**：每个事实都必须能追溯到可信来源
- **交叉验证**：关键信息需要多个独立来源确认
- **时效性检查**：确保信息的发布时间准确
- **来源可信度评估**：优先使用权威、官方来源

## 输入

- `content_items`: 待验证的内容列表，每项包括：
  - `type`: 内容类型（fact/data/quote/case/link）
  - `description`: 内容描述
  - `claimed_source`: 声称的来源
  - `claimed_date`: 声称的发布日期（可选）
  - `url`: 相关链接（如果有）

## 验证维度

### 1. 链接可访问性验证

**验证方法**：
```bash
# 检查 HTTP 状态码
curl -I -L -s -o /dev/null -w "%{http_code}" [URL]
```

**验证标准**：
- ✅ HTTP 200：链接有效
- ⚠️ HTTP 301/302：重定向（需确认最终页面）
- ❌ HTTP 404/403/500：链接失效

**处理建议**：
- 失效链接：通过 Wayback Machine 查找历史快照
- 重定向链接：更新为最终 URL
- 无法访问：寻找替代来源或移除该内容

### 2. 时间准确性验证

**验证方法**：
- 访问原文，查找发布日期
- 检查页面元数据（`<meta property="article:published_time">`）
- 查看 URL 中的日期信息
- 使用 Google 搜索查看索引时间

**验证标准**：
- ✅ 日期准确：与声称日期一致（±1 天容差）
- ⚠️ 日期模糊：只有月份或季度信息
- ❌ 日期错误：与声称日期相差超过 3 天
- ❌ 无法确定：找不到任何发布日期信息

**特殊处理**：
- 更新时间 vs 发布时间：需明确区分
- 跨时区问题：统一按 UTC 或北京时间
- 历史内容：需说明引用的是历史观点

### 3. 内容一致性验证

**验证方法**：
- 访问原始页面，对比标题和关键内容
- 检查引用是否断章取义
- 确认数据的上下文是否完整

**验证标准**：
- ✅ 完全一致：标题、数据、观点与原文一致
- ⚠️ 部分一致：有细微差异但不影响本意
- ❌ 不一致：标题或关键信息与原文不符
- ❌ 断章取义：引用脱离原文语境

### 4. 来源可信度评估

**来源分级**：

**一级来源（⭐⭐⭐⭐⭐）**：
- 官方网站：OpenAI, Google AI, Microsoft, AWS 等官方博客
- 学术论文：arXiv, ACM, IEEE 等学术平台
- 知名媒体：TechCrunch, The Verge, Wired, MIT Technology Review
- 权威机构：Gartner, IDC, Forrester 等研究机构
- 技术大牛：知名技术专家的个人博客（如 Andrej Karpathy）

**二级来源（⭐⭐⭐⭐）**：
- 技术社区：Medium（知名作者）, Dev.to, Hacker News
- 科技媒体：36Kr, InfoQ, CSDN（精选内容）
- 公司博客：Netflix TechBlog, Airbnb Engineering 等
- GitHub 仓库：官方文档和 README

**三级来源（⭐⭐⭐）**：
- 技术博客：个人技术博客（需验证作者背景）
- 社区问答：Stack Overflow（高赞回答）
- 知乎专栏：V 认证专家的回答
- 公众号文章：知名技术公众号

**不可信来源（❌）**：
- 营销软文
- 内容农场
- 未经验证的社交媒体言论
- 匿名来源
- 二手转载（无原始来源）

### 5. 数据验证

**数据类型验证**：

**统计数据**：
- 必须有明确来源（研究机构、公司报告）
- 数据范围和统计方法需明确
- 样本量和时间范围需说明

**技术参数**：
- 必须来自官方文档或论文
- 版本信息需明确（如"GPT-4 的上下文长度"需说明具体版本）
- 需注意参数的适用条件

**市场数据**：
- 优先使用权威机构报告（Gartner, IDC）
- 注意数据的统计口径差异
- 多个来源数据不一致时需说明

**验证流程**：
```markdown
1. 定位原始数据来源
2. 访问原始报告/论文
3. 确认数据的统计口径、时间范围
4. 检查是否有其他来源的相似数据
5. 如有差异，分析原因并说明
```

### 6. 引用验证

**直接引用**：
- 必须逐字核对，不得改动
- 使用引号标注
- 标明出处和页码（如适用）

**间接引用**：
- 必须忠实原意，不得曲解
- 需提供原文链接
- 如有解读，需与原意区分

**观点引用**：
- 确认该观点确实由被引者提出
- 不能张冠李戴
- 需提供完整上下文

## 验证流程

### 步骤 1：建立验证清单

```markdown
# 内容验证清单

## 待验证内容概览
- 总计事实数：[数量]
- 总计数据点：[数量]
- 总计引用：[数量]
- 总计案例：[数量]
- 总计链接：[数量]

## 验证标准
- [ ] 所有链接可访问（HTTP 200）
- [ ] 所有日期准确无误
- [ ] 所有来源可信度 ≥ ⭐⭐⭐
- [ ] 关键信息有交叉验证
- [ ] 无编造内容
```

### 步骤 2：逐项验证

**对每个内容项**：
1. 确定验证类型（事实/数据/引用/案例）
2. 访问原始来源
3. 记录验证结果
4. 评估可信度
5. 标记验证状态

**验证模板**：
```markdown
### [内容 ID]: [内容描述]

**类型**: [fact/data/quote/case]

**声称来源**: [来源名称]

**验证步骤**:
1. 链接访问: ✅/❌ [HTTP状态码]
2. 时间验证: ✅/⚠️/❌ [实际日期 vs 声称日期]
3. 内容一致: ✅/⚠️/❌ [对比结果]
4. 来源可信: ⭐⭐⭐⭐⭐ / ⭐⭐⭐⭐ / ⭐⭐⭐

**交叉验证**:
- 来源 1: [链接] - [可信度]
- 来源 2: [链接] - [可信度]
- 来源 3: [链接] - [可信度]
- 一致性: ✅/⚠️/❌

**验证结论**: ✅ 通过 / ⚠️ 需修正 / ❌ 需移除

**修正建议**: [如需修正，提供建议]
```

### 步骤 3：交叉验证关键信息

**关键信息定义**：
- 核心论点的支撑证据
- 重要数据和统计
- 颠覆性观点
- 可能引起争议的内容

**交叉验证要求**：
- 至少 3 个独立来源
- 来源类型多样（如：官方+媒体+学术）
- 来源之间无引用关系（避免循环引用）

**验证记录**：
```markdown
## 关键信息交叉验证

### 核心论点 1: [论点描述]

**来源 1**: [链接]
- 类型: [官方/媒体/学术/专家]
- 可信度: ⭐⭐⭐⭐⭐
- 支持度: 完全支持 / 部分支持 / 不支持
- 关键证据: [摘要]

**来源 2**: [链接]
- 类型: [官方/媒体/学术/专家]
- 可信度: ⭐⭐⭐⭐
- 支持度: 完全支持 / 部分支持 / 不支持
- 关键证据: [摘要]

**来源 3**: [链接]
- 类型: [官方/媒体/学术/专家]
- 可信度: ⭐⭐⭐⭐
- 支持度: 完全支持 / 部分支持 / 不支持
- 关键证据: [摘要]

**综合结论**: 
- 一致性: 高/中/低
- 可信度: 高/中/低
- 是否保留: ✅/⚠️/❌
- 修改建议: [如有]
```

## 验证工具

### 推荐工具

**链接验证**：
```bash
# 单个链接验证
curl -I -L [URL]

# 批量验证（使用 xargs）
cat links.txt | xargs -I {} curl -I -L -s -o /dev/null -w "{}:%{http_code}\n" {}
```

**日期提取**：
```bash
# 使用 curl + grep 提取发布日期
curl -s [URL] | grep -E 'published_time|datePublished|article:published'
```

**网页快照**：
- Wayback Machine: https://web.archive.org/
- Google Cache: `cache:[URL]`

**来源查证**：
- Google Scholar: 学术论文
- Crunchbase: 公司信息
- LinkedIn: 作者背景

### 自动化脚本（可选）

创建 `verify_links.py` 用于批量验证链接：

```python
import requests
from urllib.parse import urlparse
import csv

def verify_link(url, timeout=10):
    try:
        response = requests.head(url, timeout=timeout, allow_redirects=True)
        return {
            'url': url,
            'status': response.status_code,
            'final_url': response.url,
            'accessible': response.status_code == 200
        }
    except Exception as e:
        return {
            'url': url,
            'status': 'ERROR',
            'final_url': None,
            'accessible': False,
            'error': str(e)
        }

# 使用示例
links = [
    'https://openai.com/blog/...',
    'https://techcrunch.com/...',
    # ...
]

results = [verify_link(url) for url in links]

# 生成报告
for r in results:
    status = '✅' if r['accessible'] else '❌'
    print(f"{status} {r['url']} - {r['status']}")
```

## 常见问题处理

### Q1: 链接失效但内容确实存在过
**解决方案**：
1. 使用 Wayback Machine 查找历史快照
2. 搜索相同内容的其他来源
3. 如果是重要内容，注明"原链接已失效，内容来自历史快照"

### Q2: 多个来源数据不一致
**解决方案**：
1. 分析统计口径差异
2. 选择最权威的来源
3. 如差异显著，在文中说明"不同来源数据存在差异"

### Q3: 无法确定发布日期
**解决方案**：
1. 检查 URL、页面元数据
2. 使用 Google 搜索查看索引时间
3. 如无法确定，使用模糊表述"约在 X 月发布"

### Q4: 引用来自社交媒体（Twitter/微博）
**处理建议**：
- 确认账号真实性（认证账号）
- 如为重要观点，寻找正式渠道的二次确认
- 注明"根据其在 Twitter 的表述"

### Q5: 技术论坛或 GitHub Issue 中的信息
**处理建议**：
- 确认发言者身份（是否为项目维护者）
- 是否有官方确认
- 标注为"社区讨论"而非官方观点

## 输出

验证完成后，输出以下内容：

1. **验证报告**（Markdown 格式）
2. **修改建议列表**（可直接用于修改文章）
3. **验证通过的内容清单**（可用于参考文献）
4. **问题内容清单**（需要作者关注）
