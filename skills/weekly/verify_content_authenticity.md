# 验证内容真实性

对每条生成的周刊内容进行真实性验证，确保内容是真实的、时效性正确的、来源可靠的。

## 核心原则

**零容忍编造**：绝对不允许编造内容、虚构发布日期或伪造链接
**实证主义**：每条内容都必须有可验证的来源和证据——必须通过 `fetch_webpage` 工具实际访问过
**工具验证**：所有验证必须通过工具执行，不能凭 AI 记忆或推测判断真实性
**时间精确**：验证发布时间是否在时间范围内，日期必须从实际网页中提取
**立即执行**：收到指令后必须立即开始验证，不得以日期为由拒绝
**来源可靠**：优先选择官方博客、知名技术媒体、GitHub 官方仓库等可信来源

### ⚠️ 反幻觉警告
AI 模型可能会"编造"看起来合理但实际不存在的 URL、新闻事件和数据。验证时必须：
- 实际用 `fetch_webpage` 访问每个 URL，而非仅仅"看起来合理"就判定为真
- 如果 URL 返回 404/403/500，该内容必须立即丢弃，不得保留在周刊中
- 不得假设某篇文章"应该存在"或"大概率存在"

## 输入

- `content_list`: 待验证的内容列表（包含标题、URL、发布日期、来源等）
- `start_date`: 周刊起始日期（YYYY-MM-DD）
- `end_date`: 周刊结束日期（YYYY-MM-DD）
- `content_type`: 内容类型（news/blog/tool/project）

## 验证流程

### 步骤 1：访问验证（Accessibility Check）

对每条内容的 URL 进行访问验证：

**使用 Web Fetch 或浏览器访问**：
1. 访问原始链接，确认页面可访问
2. 检查是否返回 HTTP 200 状态
3. 确认页面内容与标题匹配
4. 处理重定向，使用最终 URL

**验证标准**：
- ✅ **通过**：页面可访问，HTTP 200
- ⚠️ **警告**：重定向、需要登录、区域限制（需要说明）
- ❌ **失败**：404、500 错误、无法访问

**失败处理**：
- 立即从内容列表中移除该项
- 记录失败原因
- 不要使用任何无法访问的链接

### 步骤 2：时间验证（Time Verification）

严格验证发布时间是否在周刊的时间范围内：

**验证方法**：
1. **直接提取**：从页面中查找发布日期（meta 标签、结构化数据、正文中的日期）
2. **多源对比**：对比页面显示日期、meta 标签、URL 中的日期
3. **格式识别**：识别各种日期格式（ISO 8601, "Jan 20, 2026", "2026-01-20" 等）

**查找位置**（优先级从高到低）：
1. HTML meta 标签：`<meta property="article:published_time">`
2. JSON-LD 结构化数据：`"datePublished"`
3. 页面正文中的日期标注
4. URL 路径中的日期（如 `/2026/01/20/article`）

**验证标准**：
- ✅ **精确匹配**：发布日期在 `[start_date, end_date]` 范围内
- ⚠️ **边界情况**：发布日期在范围前后 1 天内（可能是时区差异，需要说明）
- ❌ **超出范围**：发布日期明显早于起始日期或晚于结束日期

**时间验证规则**：
```
如果 start_date = 2026-01-20, end_date = 2026-01-26
搜索范围 = [2026-01-20, 2026-01-26]

- ✅ 发布日期 = 2026-01-22 → 通过
- ✅ 发布日期 = 2026-01-26 → 通过
- ⚠️ 发布日期 = 2026-01-27 → 警告（可能是时区差异）
- ❌ 发布日期 = 2026-01-15 → 失败（早于起始日期）
- ❌ 发布日期 = 2026-02-01 → 失败（晚于结束日期）
```

**无法确定日期的处理**：
- 如果页面没有明确的发布日期，使用 Web Search 搜索该内容标题，查看其他来源的发布时间
- 如果仍然无法确定，标记为 ⚠️ 警告，需要人工审核或移除

**失败处理**：
- 从内容列表中移除不符合时间范围的内容
- 在验证报告中说明移除原因和实际发布时间
- **触发补充机制**：记录被移除内容的类型和数量，用于后续补充

### 步骤 3：内容真实性验证（Content Authenticity Check）

验证内容本身的真实性和准确性：

**对于新闻类内容（news）**：
1. **交叉验证**：搜索是否有其他可靠来源报道同一事件
2. **官方确认**：对于重大新闻，查找官方公告或声明
3. **细节核对**：验证新闻中的关键事实（人名、公司名、数字等）

**对于博客文章（blog）**：
1. **作者验证**：确认作者身份（官方博客、知名技术专家等）
2. **平台验证**：确认发布平台的可信度（Medium、Dev.to、公司官方博客等）
3. **内容质量**：检查是否有实际代码、案例研究、技术细节

**对于 GitHub 项目（project/tool）**：
1. **使用 fetch_github_info skill**：获取真实的 Star 数、Fork 数、最后更新时间
2. **活跃度验证**：检查最近的 commits、issues、releases
3. **描述匹配**：确认项目描述与推荐理由一致
4. **Stars 范围验证**：
   - ⭐ 1k-10k: 新兴项目或专业领域工具
   - ⭐ 10k-50k: 成熟的开源项目
   - ⭐ 50k+: 非常流行的项目
   - ⚠️ < 100 stars: 需要特别说明为什么值得推荐（如全新项目、专业领域等）

**对于工具和资源（tool/resource）**：
1. **功能验证**：访问官网或 GitHub，确认功能描述准确
2. **可用性验证**：确认工具可以下载或在线使用
3. **文档完整性**：检查是否有使用文档或示例

### 步骤 4：来源可信度评估（Source Credibility Assessment）

评估内容来源的可信度：

**官方来源（最高可信度）**：
- 科技公司官方博客（AWS Blog, Google Blog, Microsoft Blog 等）
- 开源基金会官方网站（CNCF, Linux Foundation 等）
- 项目官方 GitHub 仓库和文档
- 权威技术媒体（The Verge, TechCrunch, Ars Technica 等）

**社区来源（高可信度）**：
- 知名技术博客平台（Medium, Dev.to）
- 行业专家个人博客（需要验证作者身份）
- GitHub Trending（官方榜单）
- Hacker News（社区投票）

**需要额外验证的来源**：
- 个人博客（需要验证作者技术背景）
- 聚合类网站（需要追溯原始来源）
- 营销性质的内容（需要识别并过滤）

**不可信来源（禁止使用）**：
- 无法验证身份的匿名来源
- 明显的营销软文
- 转载文章（必须找到原始来源）

### 步骤 5：生成验证报告（Verification Report）

为每条内容生成验证状态：

```markdown
## 验证报告

### ✅ 通过验证（XX 条）

1. **标题**: [文章标题]
   - **URL**: https://example.com/article
   - **来源**: AWS Blog
   - **发布日期**: 2026-01-22 ✅（在范围内：2026-01-20 ~ 2026-01-26）
   - **访问状态**: HTTP 200 ✅
   - **可信度**: 官方来源 ✅
   - **验证时间**: 2026-01-31 14:30 UTC
   - **验证证据**: 
     - 页面 meta 标签显示：`<meta property="article:published_time" content="2026-01-22T10:00:00Z">`
     - 原始 URL 可访问，内容与标题匹配

### ⚠️ 需要注意（XX 条）

2. **标题**: [文章标题]
   - **URL**: https://example.com/article2
   - **来源**: Medium
   - **发布日期**: 2026-01-27 ⚠️（超出范围 1 天，可能是时区差异）
   - **访问状态**: HTTP 200 ✅
   - **可信度**: 社区来源 ⚠️
   - **建议**: 建议保留，但需说明发布时间略晚

### ❌ 未通过验证（XX 条）

3. **标题**: [文章标题]
   - **URL**: https://example.com/old-article
   - **发布日期**: 2026-01-10 ❌（早于起始日期 2026-01-20）
   - **移除原因**: 发布时间不在周刊范围内
   - **建议**: 从内容列表中移除

4. **标题**: [项目名称]
   - **URL**: https://example.com/404
   - **访问状态**: HTTP 404 ❌
   - **移除原因**: 链接无法访问
   - **建议**: 从内容列表中移除
```

## 自证清单（Self-Verification Checklist）

在完成验证后，必须能够回答以下问题：

### 关于真实性
- [ ] 每个链接都能正常访问吗？（没有 404 或错误）
- [ ] 每个内容的标题与实际页面内容一致吗？
- [ ] 所有 GitHub 项目的 Star 数都是实时获取的真实数据吗？
- [ ] 所有引用的数据（数字、日期、人名）都能在原始页面找到吗？

### 关于时效性
- [ ] 每条内容的发布日期都明确标注了吗？
- [ ] 所有内容的发布日期都在 `[start_date, end_date]` 范围内吗？
- [ ] 对于无法确定日期的内容，是否已经移除或标记？
- [ ] 是否有任何"旧闻"被误当作"最近发生"的事件？

### 关于来源
- [ ] 每条内容都有明确的来源标注吗？（官方博客、知名媒体等）
- [ ] 是否过滤掉了明显的营销软文和低质量内容？
- [ ] 对于个人博客的内容，作者的技术背景是否可信？
- [ ] 是否所有的转载内容都追溯到了原始来源？

### 关于完整性
- [ ] 验证报告是否包含了所有待验证的内容？
- [ ] 对于移除的内容，是否明确说明了移除原因？
- [ ] 是否为每条通过验证的内容提供了验证证据？

## 输出

返回验证结果，包括：

1. **验证统计**：
   - 总验证数量
   - 通过数量
   - 警告数量
   - 失败数量（已移除）

2. **通过验证的内容列表**（包含验证证据）

3. **警告列表**（包含警告原因和建议）

4. **已移除内容列表**（包含移除原因）

5. **验证时间戳**

6. **补充需求分析**（如果验证失败导致内容不足）：
   - 每个内容类型的最低要求数量
   - 当前通过验证的数量
   - 需要补充的数量和类型
   - 补充搜索的建议关键词

## 内容数量要求

为确保周刊质量，每个章节需要满足最低内容数量：

- **行业动态（news）**：最低 5 条，理想 6-8 条
- **深度阅读（blog）**：最低 3 条，理想 4-5 条
- **效率工具（tool）**：最低 2 条，理想 3-4 条
- **AI 相关（project）**：最低 2 条，理想 2-3 条
- **学习资源（resource）**：最低 1 条，理想 1-2 条

**补充策略**：

如果验证后某个类型的内容数量不足：

1. **放宽时间范围**：
   - 新闻类：从 7 天扩展到 10 天
   - 博客类：从 14 天扩展到 21 天
   - 工具/项目：从 30 天扩展到 60 天

2. **扩展搜索源**：
   - 增加更多知名技术博客和媒体
   - 搜索相关但稍微偏离主题的内容
   - 从 GitHub Trending 往前回溯

3. **调整搜索关键词**：
   - 使用更广泛的关键词（如 "software engineering" 代替 "DevOps"）
   - 组合多个相关领域的关键词
   - 搜索相关技术栈或工具

4. **跨类型补充**：
   - 如果某类型实在不足，可以从其他类型借用
   - 例如：将高质量的博客文章作为深度阅读推荐

## 使用示例

```
@workspace #file:weekly/verify_content_authenticity.md 验证以下内容的真实性：
- 周刊范围：2026-01-20 ~ 2026-01-26

内容列表：
1. AWS DevOps Agent 正式发布
   - URL: https://aws.amazon.com/blogs/devops/...
   - 声称发布日期：2026-01-22

2. Kubernetes 新版本发布
   - URL: https://kubernetes.io/blog/...
   - 声称发布日期：2026-01-24
```

## 注意事项

1. **宁缺毋滥**：当无法验证内容真实性时，选择移除而不是冒险使用
2. **保存证据**：保存验证过程中的关键证据（截图、HTML 源码等）
3. **定期复验**：在发布前再次验证所有链接的可访问性
4. **时区处理**：考虑不同时区的影响，对于边界日期给予 ±1 天的容差
5. **更新追踪**：如果发现内容有更新，使用最新的版本和日期

## 常见问题处理

**Q: 如果页面没有明确的发布日期怎么办？**
A: 尝试以下方法：
1. 检查 URL 路径中的日期
2. 使用 Web Search 搜索该内容，查看其他来源的发布时间
3. 如果仍无法确定，标记为警告或移除

**Q: 如果发现发布日期在范围之外但内容很重要怎么办？**
A: 严格遵守时间范围，不符合的内容应移除。如果真的很重要，可以留到下期周刊。

**Q: 内容不够怎么办？**
A: 对于内容不足的类型，可以适当放宽搜索范围（参考补充策略）。

**Q: 如何处理多个来源报道同一事件但日期不同的情况？**
A: 使用官方来源的日期为准。如果是原创报道，使用最早的可信来源日期。

**Q: GitHub 项目的 Star 数不断变化，如何确定？**
A: 使用 fetch_github_info 获取当前实时数据，并在验证报告中注明获取时间。

**Q: 如何判断一篇文章是原创还是转载？**
A: 检查页面底部的版权信息、作者声明，或使用搜索引擎查找更早的发布来源。
